# Agile Review — Actual Prototype vs Proposed Improvements

This is a suggested retrospective framework for the student team. Replace the “actual practice” wording with your team's real sprint records before submission.

| Agile area | Actual practice represented by this prototype | Proposed improvement for next sprint |
|---|---|---|
| Product backlog | Core user journeys were prioritised: discover, view, apply, save, manage listings | Convert every feature into a user story with acceptance criteria and priority |
| Sprint planning | Prototype scope grouped around student, recruiter and admin journeys | Estimate tasks, agree sprint goal and define a realistic capacity |
| Daily coordination | Team coordination is not technically captured in the prototype | 10-minute daily stand-up: done, next, blockers |
| Increment | A runnable, seeded browser prototype is available | Demo a tested increment at the end of every sprint |
| Testing | Ten functional test cases are documented | Automate API/UI regression tests and add accessibility/security checks |
| Review | Demo roles and sample data support a stakeholder walkthrough | Collect feedback from students and recruiters and record decisions |
| Retrospective | Defects and integration simulations are documented | Identify one process improvement and assign an owner for the next sprint |

## Example Sprint 2 requirement change

**Change request:** Add an opportunity work-mode filter (Remote, Hybrid, On-site, Online) to improve discovery.

**Impact:** Update the discovery filter UI, add/confirm the `mode` field in the opportunity model, test combinations with keyword/category filters, and capture before/after screenshots.

**Acceptance criteria:** A user can choose a work mode; only matching listings appear; “All modes” restores all results; the filter works with keyword and category filters together.
